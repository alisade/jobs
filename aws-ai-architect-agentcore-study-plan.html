AWS AI Architect - Agentic AI on AgentCore, cloud engineering first

6-week plan plus an optional add-on week for an AWS AI Architect contract: multi-account AWS, GitLab CI/CD, CDK and CDK Pipelines, AgentCore Runtime and Gateway, Strands, MCP, OBO identity, Cedar and AgentOps. Weekdays ~2-3 h, weekends one long block for the workbook exercises. Checkboxes save in this browser.

Overview

The role: an AWS AI Architect on a long-term contract who designs and runs secure multi-account AWS environments, GitLab CI/CD and CDK pipelines, and production agent systems on Amazon Bedrock AgentCore (Runtime, Gateway, Identity, Observability) with Strands agents, MCP integrations, OAuth on-behalf-of, Cedar policies, SSM, DynamoDB and OTEL-based AgentOps. The posting says it twice: cloud engineering and DevOps are the primary focus.

Honest fit. This is one of your strongest matches. The mandatory block (multi-account AWS, CDK, IAM and federation, CloudWatch and CloudTrail, release management, incidents) is your day job: lead with it. The gap is the agentic layer (Strands, AgentCore Runtime and Gateway, MCP servers you built, Cedar, OBO) plus a few smaller DevOps gaps you should name yourself: GitLab CI/CD syntax, CDK Pipelines, SCP authoring and Identity Center administration, SSM Automation, DynamoDB modeling. Do not claim production AgentCore, Strands or Cedar; say you built and run the platform below in a personal AWS organization, and walk through it.

End-of-plan portfolio: an enterprise agent platform starter on AWS

One public repo, CDK in TypeScript, agents in Python, synthetic data only. It should read like the platform this team is about to build.

  • Multi-account foundation: OUs, SCPs (regions, org membership, CloudTrail, approved Bedrock models) and an RCP, Identity Center permission sets
  • GitLab CI/CD with OIDC per account (no stored keys): lint, test, synth, ARM64 image build and scan, ECR, diff on the MR, dev, protected prod; plus a CDK Pipelines branch and an ADR
  • Strands orchestrator with two specialists on AgentCore Runtime, versions and a prod endpoint for rollback
  • Gateway with an OpenAPI target and a Lambda target, plus one MCP server you wrote, as a Gateway target
  • OBO identity so tools see the user; Cedar policies on the gateway rolled out LOG_ONLY then ENFORCE
  • DynamoDB for sessions, cost ledger and idempotency; AgentCore Memory for conversations
  • AgentOps: ADOT traces, a dashboard with latency, tool errors, Cedar denies, tokens and cost per conversation; Gateway data events; Agent Registry; online evaluation
  • SSM Automation runbooks (rollback, rotate secret, drain) with approvals and backups; VPC endpoints with policies

CloudMulti-account governance and SCPs

Your strongest ground; show you have authored guardrails, not just lived under them.

Rehearse

  • "Write me an SCP that restricts Regions. What breaks?"
  • "How do you test an SCP without locking out an OU?"
  • "SCP vs RCP vs permissions boundary?"

Talk track

  • Deny-list with FullAWSAccess kept; NotAction for global services; Bedrock cross-Region inference destinations allowed only with an approved inference profile ARN; break-glass via aws:PrincipalArn.
  • Missing keys: negated operators are true when the key is absent, which is what makes 'deny unless through my VPC endpoint' work; IfExists where absence must not deny.
  • Test OU with one sandbox account, a request table run through an evaluator (as in w1-c1), then watch CloudTrail for explicit-deny events for a week before widening.
  • SCPs cap principals in member accounts (never the management account or service-linked roles); RCPs cap resources (deny-only, Principal "*"; careful with web identity on STS); boundaries cap one principal.

CloudPipelines: GitLab CI/CD, CDK and CDK Pipelines

Name the gap (GitLab syntax, CDK Pipelines) and show the concepts transfer.

AgentsStrands, multi-agent patterns and MCP

Be concrete about what you built and why you chose the pattern.

Rehearse

  • "Agents as tools, swarm or graph?"
  • "Where do guardrails go in a Strands app?"
  • "Build an MCP server for our ITSM. How do you design the tools?"

Talk track

  • Start with agents as tools: easiest to bound and trace. Swarm for open-ended handoffs, graph for branching flows with loops, workflow for fixed parallel tasks; measured on quality, model calls and tokens.
  • Hooks for anything that must hold (audit, delete blocks, budgets); Cedar on the gateway for tool authorization; prompts only for behavior.
  • Task-shaped tools (create change, get change, list my open changes, comment), small outputs, actionable errors, identity from the verified token; or no server at all when an OpenAPI or Lambda target is enough.
  • State: never share an Agent across sessions (w2-t1); session managers or AgentCore Memory keyed on the session.

IdentityOAuth on-behalf-of and Cedar

Where most agent platforms get it wrong. Draw the token path.

Rehearse

  • "Why not give the agent a service account?"
  • "Explain RFC 8693 token exchange."
  • "A Cedar forbid did not stop an approval. Why might that be?"

Talk track

  • A service account makes the agent a confused deputy: the API authorizes the agent, not the user. OBO keeps the user as subject and records the agent as actor.
  • subject_token is the user's token, actor_token the agent's; the IdP issues a token for the API's audience with narrowed scope; verify audience, subject, scope and actor before use. Entra uses the JWT-bearer form.
  • AgentCore Identity: workload identity, GetWorkloadAccessTokenForJWT, an OAuth2 credential provider in token-exchange mode, GetResourceOauth2Token; the agent never sees client secrets.
  • Cedar skips a policy whose evaluation errors, so a forbid that reads a missing attribute does nothing (w4-t1). Guard with has and validate against the schema in CI; review errors in LOG_ONLY, not just decisions.

OpsAgentOps, incidents and cost

Tie your incident experience to agent-shaped telemetry.

Rehearse

  • "What is on your AgentOps dashboard?"
  • "Tool spans show up as separate traces. Debug it."
  • "Cost tripled after a release. Where do you look?"

Talk track

  • p50/p95 per agent and tool, tool error rate, throttles, Cedar denies, tokens in/out and cache hits, cost per conversation, online evaluation scores; alarms to SNS with runbooks.
  • Parallel tool calls on a thread pool lose the OTEL context unless you copy it; check parent ids and thread names in the exported spans (w5-t1).
  • Cache read tokens first: dynamic data before the cache point kills the cache (ai-t1). Then cycles per turn, tool output size, model choice; change one thing at a time against an eval.
  • Rollback is an SSM runbook that backs up the endpoint state, asks for approval, moves the endpoint and verifies the error metric (w6-c1).
