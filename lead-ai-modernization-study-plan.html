Lead AI Engineer, Application Modernization - Java, identity, safe change, agent pods

6-week plan plus an optional add-on week for a 12-month remote lead role. Weekdays ~2-3 h, weekends one long block for the workbook exercises and the portfolio. Checkboxes save in this browser.

Overview

A Senior/Lead AI Developer who triages unfamiliar enterprise applications, designs the modernization approach, builds and governs reusable AI skills and agents, and guides development pods through safe technology-stack and security upgrades (JDK, app server, dependencies, LDAP to token-based identity, .NET) while preserving the application's architecture and behaviour. Remote, 12 months. The role is half lead (triage, blast radius, incidents, agent workflows, verification) and half hands-on enterprise Java modernization.

Honest fit. You are strong on the lead half: 26 years of production incidents, triage across unfamiliar systems, approval gates and verification, and a substantial Claude Code harness. The open question is "7-10 years as a Software Engineer" with deep Java and/or .NET, especially enterprise Java modernization (JDK, JBoss, Maven). Frame it honestly: you lead and verify modernization; you are not yet a 10-year Java developer. The six weeks and the public pod kit are how you back that up with evidence.

Week 1 - JDK and Jakarta migration mechanics, Claude Code as a platform

The biggest gap in the posting is hands-on enterprise Java modernization. This week you learn exactly what breaks between JDK 8 and 21 and why, how Maven decides which jar you actually get, and you set up Claude Code the way a lead would for a pod, not just for yourself. Every upgrade step is run with tests green before and after.

MonWhat JDK 9 to 21 removed and encapsulated

Three classes of breakage cover most legacy apps: removed modules (JAXB, JAX-WS, CORBA), removed internal APIs (sun.misc.*), and strong encapsulation of java.base internals that turns reflective hacks into InaccessibleObjectException.

Tasks

  • Read the Oracle JDK 21 migration guide end to end; list every removed API and changed default that could touch a 2009-era WAR
  • Read JEP 320, JEP 396 and JEP 403; write one line each on what fails, at compile time or at runtime, and why --add-opens is a smell, not a fix
  • Read JEP 400 (UTF-8 by default) and note every place a legacy app relies on the platform charset (new FileWriter, getBytes() with no argument)
  • Clone spring-framework-petclinic; build it on JDK 8 if you have one, then on 21, and record the first error each build hits

Materials

  • Oracle JDK 21 migration guide
  • JEP 320: remove the Java EE and CORBA modules
  • JEP 396: strongly encapsulate JDK internals by default / JEP 403: strongly encapsulate JDK internals

Week 3 - LDAP to OIDC and JWT with identical authorization

Find where the legacy app hides authorization (container roles, filters, LDAP lookups in code, DB role tables, JSPs), then move it to token-based identity without changing who can do what. Everything runs locally: an embedded UnboundID LDAP server for the baseline and a local JWT issuer with its own JWKS. Okta concepts apply directly; an Okta developer account or Keycloak is optional.

MonWhere legacy apps hide authorization

Container-managed security in web.xml, custom filters doing LDAP searches, isUserInRole in servlets and JSPs, and application role tables in the database. Miss one and the migration silently widens access.

Tasks

  • Read Spring Security LDAP authentication: bind vs search, group search base, role mapping
  • Inventory every authorization check in the w2-c1 app (you already have most of them): mechanism, role, what it protects
  • Read the UnboundID in-memory directory server docs; load an LDIF with users, groups and one nested group
  • Write tests that pin who can do what (a user x action matrix) against the embedded LDAP

Materials

  • Spring Security: LDAP authentication

  • Okta: OAuth 2.0 and OIDC overview

Talk track

JavaJDK 8 to 21, Jakarta, app servers

Be precise about what breaks and why. This is where the "deep Java" question gets tested.

Rehearse

  • "What breaks when you move a Java 8 app to 21?"
  • "javax to jakarta: why can you not do it one library at a time?"
  • "What changes going from JBoss EAP 7 to 8?"
  • "A colleague added --add-opens to make it start. Thoughts?"

Talk track

  • Removed modules (JAXB, JAX-WS, CORBA: JEP 320), removed internals (sun.misc.BASE64Encoder), strong encapsulation (JEP 396/403) turning reflection into InaccessibleObjectException, changed defaults: CLDR locale data (JEP 252), UTF-8 (JEP 400), TLS and GC.
  • Jakarta EE 9 renamed the packages, so the app server, every EE library and your code must agree on one namespace. Order: app server target, libraries with jakarta releases (or Eclipse Transformer), then source with OpenRewrite, characterization tests green after each.
  • EAP 8 is Jakarta EE 10; the legacy security subsystem is gone (Elytron only), descriptors and modules change. Use MTA/Konveyor rules to find the descriptor work.
  • --add-opens is a smell: it hides a dependency on internals that will break again. Fix the code or upgrade the library; allow it only as a dated, owned exception.

MavenDependency remediation

Show you can read a dependency tree and prevent the next incident.

Rehearse

  • "The build is green but production throws NoSuchMethodError. Debug it."
  • "How do you upgrade 140 dependencies safely?"
  • "How do you handle a CVE in a transitive dependency?"

Talk track

  • NoSuchMethodError between classes of one library means two versions on the classpath. mvn dependency:tree -Dverbose: look for "version managed from" (a dependencyManagement pin overriding a transitive version) and "omitted for conflict" (nearest wins). Workbook w1-t1 is exactly this.
  • BOMs per library family, enforcer requireUpperBoundDeps and dependencyConvergence, small batches grouped by family, characterization tests per batch, Renovate with major bumps behind approval.
  • Pin a floor, not an exact version, through the BOM or a managed version that is at least the fixed release; prove it with the SBOM and the scanner; record what remains and why.

IdentityLDAP to Okta, OAuth/OIDC/JWT

Show you can move authorization without changing who can do what.

Rehearse

  • "Where does a legacy app hide its authorization logic?"
  • "How do you migrate LDAP groups to Okta without breaking access?"
  • "What do you validate on a JWT?"
  • "Some users get 401 after the IdP rotated keys. Why?"

Talk track

  • Container security in web.xml, filters with LDAP searches, isUserInRole in servlets and JSPs, DB role tables. Inventory them all first; the w2-c1 inventory has an auth section for this.
  • Okta with AD as the source directory, a groups claim with a filter, a mapping table from group to the same application roles, nested groups flattened explicitly. Prove parity with a user x action matrix that runs against embedded LDAP and against tokens.
  • Algorithm allow-list (no none, no HS256 with a public key), issuer, audience, exp/nbf with bounded skew, kid lookup in the JWKS. RFC 8725.
  • JWKS cached forever: tokens signed with the new key have an unknown kid. Refresh on unknown kid with a cooldown, honour cache headers. Workbook w3-t1.

Safe changeChanging a monolith without breaking it

The posting is explicit: preserve the architecture, assess blast radius, plan rollback.

Rehearse

  • "How do you prove a modernization did not change behaviour?"
  • "What is in your blast-radius assessment?"
  • "Would you split this monolith into microservices?"
