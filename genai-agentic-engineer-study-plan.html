AI Engineer, GenAI / Agentic Development - full stack, production GenAI, responsible AI

6-week plan plus an optional add-on week. Weekdays about 2-3 h, weekends one long block for the workbook exercises. Checkboxes save in this browser.

Overview

The role: an AI Engineer who designs, builds and deploys production-grade GenAI and agentic applications end to end, full stack in Python, TypeScript and React, on a microservice architecture, using AI coding assistants and agentic development workflows at an expert level. It also asks for responsible AI (bias, safety, reliability), integrating agents into existing enterprise apps, mentoring and technical decisions, Agile with Jira and Confluence, and (preferred) retail experience. San Francisco, hybrid 2 days a week, 12+ months fixed term.

Honest fit note. This is an application engineer role with a GenAI focus, not a platform or DevOps role. Its centre is full-stack Python, TypeScript and React, microservices, and "2+ years focused on AI/ML or Generative AI applications". Your strongest material (deploying, operating and securing systems, and running an agent harness) covers the edges of this job, not its centre. React and application backend code are real gaps; your AI work is heavy and real but it is tooling for your own engineering, not shipped AI products for users, so do not claim otherwise. Frame it as agentic development workflows in production use and back it with the portfolio. Responsible AI vocabulary and retail are new. Expect a live coding or take-home round in Python or React. The pitch that works: someone who can ship a GenAI app all the way to production and keep it running, and who already uses agentic coding at an expert level.

DesignDesign the shopping assistant end to end

The core whiteboard. Draw it left to right: React panel, gateway/CDN, assistant service, tools, catalog and orders services, model gateway, evals and observability.

Rehearse

  • "What happens when the model provider is slow or down?"
  • "How do you stop it inventing prices?"

Talk track

  • Start from the user and the metric: conversion and contact deflection, without more recontacts or returns. Name the latency target (time to first token) and the cost budget per conversation.
  • React panel streams over SSE through the CDN with buffering off and keepalives. The assistant service runs the loop with read tools; writes become pending actions the customer confirms.
  • Catalog and orders stay owned by their teams, called through their APIs with the customer's identity. Prices and stock are rendered from structured tool output, never from model text.
  • Resilience: timeouts sized to the output budget, retries only for 429/529 with backoff, one fallback model behind a gateway interface, one attempt budget, circuit breaker, a human handoff path.
  • Close with operations: traces per model and tool call, token cost per request, eval gate in CI, system card.

CodeLive coding: React streaming component and a FastAPI endpoint

Expect one of these in 40-60 minutes. Narrate decisions as you type.

Rehearse

  • "Render a streamed model answer with a Stop button and error states."
  • "Write an endpoint that calls the model and a tool, with tests and no real API calls."

Talk track

  • React: an AbortController per run, functional state updates, a run id so stale runs cannot write, stop keeps partial text, an end without done is an error, roles for the log and alert.

  • Duplicates: resume from the last complete event id or replace the text; make the reducer idempotent on event id (workbook w1-t1).

ArchMicroservices trade-offs

Show you know the operating cost of every boundary; that is your differentiator.

Rehearse

  • "Would you make the assistant a separate service?"
  • "Sync or async between assistant and catalog?"
  • "Where does model fallback live: in the assistant or a shared LLM gateway?"

Talk track

  • Split on ownership and operational difference: a separate team, long streaming requests and model spend justify a service; otherwise a module is cheaper. Monolith first when the domain is new.
  • Reads are sync with deadlines and batch endpoints; state changes across services use events or a saga with compensation.
  • A shared gateway centralises auth, quotas, cost attribution and fallback but is one more critical dependency with its own SLO; start in the assistant behind an interface, extract when a second consumer appears. Record it as an ADR with the rejected options.
  • Resume hook: years running microservices on EKS with Helm and ArgoCD, so you can say what each extra service costs in on-call and deploys.

ProdProduction GenAI: cost, latency, rate limits

Be concrete with numbers and mechanisms.

Rehearse

  • "Your model bill went up 9x overnight. Walk me through it."
  • "How do you keep p95 latency in budget?"
  • "How does prompt caching affect your design?"

Talk track

  • Group the usage export by request fingerprint: repeated identical requests mean retries. Look for timeouts shorter than generation (billed but discarded), retries on non-retryable errors, and fallbacks with their own retries (workbook w3-t1).
  • Latency: stream for time to first token, parallel tool calls, batch downstream calls, deadlines propagated, smaller model for routing, cache static answers by data class.
  • Caching: byte-stable static prefix (system prompt, sorted tools) before the breakpoint, dynamic data after; monitor cache read tokens per worker (workbook ai-t1).
  • Track tokens and cost per attempt, including discarded attempts, with OTel GenAI attributes.
