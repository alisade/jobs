AI Engineer, Agentic Audit Controls Testing - Gemini, ADK, review gates, evidence, evals

6-week plan plus an optional add-on week. Weekdays ~2-3 h, weekends one long block for the workbook exercises. Checkboxes save in this browser.

Overview

The role: one of three hands-on AI engineers building an agentic application that automates audit controls testing. Agents retrieve evidence, call tools and run multi-step control tests with human review where needed, on an orchestration layer that executes reusable skills, keeps state, recovers from errors and tracks execution. Azure provides compute and storage, Google Gemini is the model, and Gemini Enterprise Agent Platform is in scope. Every result must trace to its supporting evidence, with evaluations, logging, access controls and review checkpoints, and accuracy, consistency and cost measured per control.

Names changed. Google now calls Vertex AI's generative and agent platform Gemini Enterprise Agent Platform. Its docs live under docs.cloud.google.com/gemini-enterprise-agent-platform/..., and Agent Engine is now documented as "scale and deploy agents". The posting uses the new name. Tutorials, Stack Overflow answers and many interviewers still say Vertex AI and Agent Engine, so use both names.

Honest fit

Good fit, with specific gaps. You already run the hard parts of this job on infrastructure: approval gates, scoped permissions, least privilege, change management, "back up before mutate", multi-step pipelines with retries and idempotency, and a daily Claude Code setup that is a working skills harness. You have also produced ITGC evidence as the auditee in regulated environments (SOX-relevant financial services, federal NIST 800-53).

The gaps, most important first:

  1. Building agents in Python code rather than configuring them.
  2. Google's agent stack (google-genai, ADK, Gemini Enterprise Agent Platform).
  3. Stateful orchestration with human review.
  4. Grounding with page- and cell-level citations.
  5. Evals per control.
  6. The tester's audit vocabulary.
  7. Azure-to-Google auth without keys.

Be upfront in interviews: you have not shipped an audit agent yet, and the portfolio project is how you show the build.

Portfolio project: ITGC change-management control tester

  1. Pull a population of merged PRs and change tickets (W2, w2-c1).
  2. Draw a sample sized to the control frequency (W2).
  3. For each item, an agent checks four attributes: approval before deploy, a linked ticket, an approver who is not the author, and passing tests (W1, W3, w1-c1, w3-c1).
  4. Stop at a human review gate for every exception (W4, w4-c1).
  5. Produce a workpaper where every conclusion cites its evidence (W5, w5-c1).
  6. Report accuracy, consistency and cost per control from an eval suite (W6, w6-c1).

Stack: Python, Gemini via google-genai and ADK, Pydantic, Azure. Put it in a public repo and use synthetic or open-source data only. Each workbook coding exercise is one part of it. The troubleshooting exercises are the failure stories you tell about it.

One-line pitch: "I make agents safe and operable in production. Write tools sit behind approval gates, and there is a trail an auditor can follow to reconstruct what the agent did."

How this applies to this role

Agentic audit controls testing: all seven areas apply, with no model training. The model is Gemini (through google-genai and ADK, on the Gemini API or Gemini Enterprise Agent Platform), and the work around it is integration discipline under an auditor's standard of evidence. The Build tasks above can be done against Claude as written; then do each one again in Python against Gemini so you know where the APIs differ.

  • Tools (1) and the loop (2): Gemini function declarations with automatic calling disabled so every call is allow-listed and logged; ADK tools with before/after tool callbacks as the deterministic guard (W1 Thu, W3 Wed). GRC, identity and ticketing systems become MCP servers with read-only tools and gated writes.
  • Context and caching (3): one sample per context: the control procedure and tool list as a byte-stable prefix, the sample's records last. Gemini implicit and explicit context caching keep a long control procedure cheap; a timestamp at the top of the system instruction breaks it (W6 Wed).
  • Security (4): evidence files are untrusted input and may carry instructions. The agent that reads evidence has no write tools; exception closures pass a human review gate; identities are scoped per component (W5 Thu, W4 Fri).
  • Evals (5): a labeled set per control, exception recall as the gate, agreement across five runs, dollars per 100 samples; labels from humans only, with provenance (W6).
  • RAG (6): Document Intelligence layout with page and cell locators, hybrid search with RRF, citations verified in code, "insufficient evidence" instead of a guess (W5).
  • Observability (7): an append-only, hash-chained execution log for the auditor plus OTel GenAI spans for engineers; usage metadata per call for cost (W4 Wed).

Practice: ai-c1 (GRC MCP server with a gated write tool, coding) and ai-t1 (cost up after a prompt refactor broke implicit caching, troubleshooting).

Interview prep

These are the questions this posting is likely to bring, each with a talk track. Rehearse every question aloud: answer in 2 minutes, then give the 30-second version. Tick a question once you can do both without notes. Interviewers will come from engineering and from audit, so practice each answer in both registers.

DesignWalk me through an agent that tests a change-management control end to end

The core whiteboard. Draw it left to right: population, sample, evidence, extraction, rules, review gate, workpaper, evals.

Rehearse

  • "Design an agentic application that tests CM-03 for 30 applications every quarter."
  • "Which steps use the model and which do not, and why?"
  • "What does the auditor receive at the end?"

Talk track

  • Start with the auditor's question and the evidence chain. The population comes from the deploy log and reconciles to a control total (IPE). The sample is seeded and reproducible. No model touches either step.
  • The model reads messy evidence (tickets, PRs, e-mails) and returns typed facts with citations, validated by Pydantic with a retry. Code applies the attribute rules: approval before deploy, compared in UTC; an independent approver, resolved through the directory; the linked change; tests passed.
  • Exceptions and not-evaluable items stop at a human review gate. The reviewer is never the preparer, and an override needs a reason and an evidence reference.
  • Output: a workpaper row per sample with page- or cell-level citations, plus an execution log the auditor can replay and an eval report per control.
  • Stack: Python, google-genai and ADK on Gemini Enterprise Agent Platform, an Azure-hosted orchestrator (Durable Functions or Container Apps), evidence and workpapers in immutable Blob storage, and Workload Identity Federation so there are no keys.

HarnessReusable skills and the orchestration layer

The preferred qualification is a harness that loads and executes reusable skills. Treat your Claude Code setup as the reference design.

Rehearse

  • "Have you built an AI harness that loads reusable skills?"
  • "How would a new control be added without touching the orchestrator?"
  • "How do you version and govern skills?"

Talk track

  • Be honest and concrete: you run a daily harness (skills with trigger descriptions, hooks as deterministic gates, MCP servers, permission modes) and you designed ControlPilot's skill format on the same principles.
  • One skill per control holds the trigger, inputs, the tools allowed (scoped by the orchestrator, not by the skill text), the verification step, the approval point and an eval set.
  • Skills are program changes for ControlPilot itself. They go through review, an eval gate in CI and a pinned model and prompt version, so the agent is an ITGC subject too.
  • Progressive disclosure: only the short descriptions load first, which keeps the context small when there are 30 controls.

StateState, human review and error recovery

Show you think in checkpoints and idempotency, not chat history.

Rehearse

  • "A run of 400 samples dies at sample 212. What happens?"
  • "A reviewer takes three days. Where is the state?"
  • "How do you stop a retry from creating duplicate issues in the GRC system?"

Talk track

  • Checkpoint every step per sample in a durable store (ADK DatabaseSessionService, Durable Functions or Temporal). A resume skips completed steps and never repeats a model call whose result is recorded.
  • The review gate is an interrupt: the sample is parked as awaiting_review and the run continues with other samples. The decision is recorded with the reviewer, the reason, the evidence and a timestamp.
  • Side effects carry an idempotency key derived from (run, sample, step), sent on every attempt. Record the intent before the call. Commit-then-timeout is the case to design for (w4-t1).
  • ADK specifics: state scopes (session, user:, app:, temp:), and the fact that temp: is dropped after every invocation (w3-t1).

EvidenceTraceability, grounding and citations

"Results traceable to supporting evidence" is the line the audit stakeholders care about most.

Rehearse

  • "How do you prove a conclusion came from the evidence and not from the model?"
  • "Evidence is a scanned PDF with a table. Walk me through it."
  • "What does the agent do when evidence is missing?"

Talk track

  • Layout parsing (Document Intelligence) keeps the page, paragraph, table, row and column on every chunk. Retrieval is hybrid (BM25 plus vectors, fused with RRF).
  • The model returns claims with quotes and locators. Code verifies each quote verbatim at the cited location, and a conclusion without a verified citation is rejected.
  • If the evidence is missing or contradictory, the answer is insufficient_evidence and the sample goes to a human; the agent never guesses. Evidence that is a system export needs its IPE documented.
  • Managed grounding on the platform is useful, but you still verify citations yourself, because the auditor relies on your verification, not the vendor's.

SecuritySecuring an agent that reads enterprise evidence

Prompt injection through evidence files, the lethal trifecta, scoped tools.

Rehearse

  • "An approval e-mail contains text telling the agent to close the exception. What happens?"
  • "How do you scope the agent's access?"
  • "What can the agent do without a human?"

Talk track

  • Evidence is untrusted input. The agent that reads it has read-only tools; closing an exception or changing a conclusion needs a human approval record (w5-t1). Prompt wording is not a control.
  • Break the lethal trifecta: private data plus untrusted content plus an outbound or write channel. Remove the channel from any agent that sees untrusted content.
  • Scope tools to the sample in a callback; give each component its own identity (managed identities, Workload Identity Federation); keep secrets out of the model context; redact PII before the model sees it.
  • Everything the agent does lands in an append-only log that sits outside the agent's reach.

EvalsMeasuring accuracy, consistency and cost per control

Numbers, not adjectives.

Rehearse

  • "How do you know the agent is accurate enough to rely on?"
  • "What metric would you gate a release on?"
  • "What does it cost per control?"

Talk track

  • A labeled set per control (30 samples or more), labeled by humans and with provenance; model output can never become a label (w6-t1).
  • Gate on exception recall, because a missed exception is the costly error. Also track per-attribute accuracy, precision and agreement over five runs (modal agreement, Fleiss' kappa), and route low agreement to a human.
  • Cost per 100 samples comes from usage metadata and the price table, with cached tokens discounted; keep the prefix stable so the cache hits. Track p50 and p95 latency per sample.
  • Any prompt, model or schema change runs the eval suite in CI and attaches the report to the change ticket.

AuditAudit vocabulary, so the stakeholders trust you

You will be interviewed by audit and risk people too. Use their words precisely.

Rehearse

  • "What is the difference between design and operating effectiveness?"
  • "How big is your sample and why?"
  • "Is a self-approved emergency change a deficiency?"

Talk track

  • Design: would the control prevent or detect the risk if it operated as described. Operating effectiveness: did it operate throughout the period, tested on a sample.
  • Sample size follows control frequency and risk from the firm's table. A common rule of thumb is about 25 for a daily or recurring control and 2 for a quarterly one. The selection is random, seeded and documented.
  • An exception is an instance where an attribute failed. Whether it amounts to a deficiency, a significant deficiency or a material weakness is the auditor's judgement. The agent reports exceptions with evidence and never decides severity.
  • Population completeness and accuracy (IPE) comes before any sampling.
