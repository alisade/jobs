Backend data platform workbook

Hands-on coding, troubleshooting and design exercises for Keystone, the platform layer that Lumenfold (a fictional enterprise data and AI company) is building to move its internal apps off a third-party CRM. One tab per study week, weekly self-exams and a timed technical screen. Everything grades locally and offline: no cloud accounts, no API keys, no Docker.

Scores update after /grade; reload the page. Grades come from ../grades/grades.js, written by tools/update_grades.py when you run /grade backend/<id> in Claude Code from the workbooks/ folder. Quiz answers and mock results save in this browser (localStorage key wb-backend-v1).

How to work an exercise

  1. tools/doctor.sh backend once: python3, uv, node 22, go, jq. make deps in backend/ installs the shared toolchain in one go (about 30 s).
  2. Open the week tab, read the card, then the folder README.
  3. cd backend/exercises/<id> && make setup (first run installs the shared toolchain into backend/_env), solve it, make test, fill in ANSWER.md.
  4. From workbooks/: /grade backend/<id>. Reload this page.
  5. make clean. Retry as often as you like; every attempt is kept.

Do not open .grading/ before you submit. Pass mark 70/100. Troubleshooting is graded mostly on root cause and evidence; design exercises are graded by rubric only (the grader reports 0/0 tests and the automated row does not apply).

How the local stand-ins work

  • PostgreSQL: PGlite, real PostgreSQL 18 compiled to WebAssembly and installed with npm. The planner, RLS, constraints and EXPLAIN are the real thing; it is a single session, so lock waits are studied from captured pg_locks evidence instead.
  • Python services: FastAPI and SQLAlchemy 2 async on SQLite (aiosqlite) where the exercise is about the service, not Postgres; pytest with httpx against the ASGI app.
  • TypeScript services: Fastify, Kysely (PGlite dialect), Zod, graphql-js and DataLoader, tested with jest.
  • Kafka: an in-process partitioned log with offsets, consumer groups and redelivery. Temporal: the real Python SDK with its time-skipping test server (downloaded once by make deps) and the offline Replayer.
  • MCP: the official Python SDK, called in process; the "model" is a scripted client, so no API key is needed. Go: standard library only.

Keystone core schema with tenancy enforced in the database

coding 2-3 h

backend/w2-c1 · PostgreSQL: modeling, indexing, RLS, migrations

Scenario. Lumenfold's security review says tenancy in Keystone is enforced by PostgreSQL, not by every developer remembering a WHERE clause, and the CRM's validation rules become constraints an agent cannot route around. Idempotency keys that survive concurrent retries

coding 2-3 h

backend/w3-c1 · API design: REST, GraphQL, idempotency, pagination

Scenario. accounts-svc (FastAPI, async SQLAlchemy 2) accepts Idempotency-Key on its POSTs, but the first version checks then inserts. During a load test with retrying workflow activities and agents, 20 retries of one request created several accounts. Make the key a real guarantee.

Task

  • Require the Idempotency-Key on POST, scoped per tenant (400 problem if missing or too long)
  • Claim the key atomically by INSERT under the unique key, store a request fingerprint and the response
  • Replay completed responses with Idempotent-Replayed: true; 422 for a different request; 409 + Retry-After while in progress
  • Release the key when the handler fails or returns 5xx; expire keys after 24 h
  • All errors as RFC 9457 application/problem+json

Acceptance criteria

  • 20 concurrent identical requests create exactly one account; the rest are replays or 409s
  • Fingerprint covers method, path and a canonical body (key order and whitespace do not matter)
  • A failed attempt can be retried with the same key; stored 4xx outcomes are replayed
  • Keys are per tenant; expired keys behave like new ones

Idempotent timeline consumer in Go

coding 2-3 h

backend/w5-c1 · Go

Scenario. Keystone's timeline-consumer reads ActivityLogged, ActivityEdited and ActivityDeleted events (keyed by account) and builds the account timeline and live activity counter that sales sees. The relay and the topic are at-least-once, producers retry, and the spike version double counts, resurrects deleted activities and stalls on one bad message. Make it correct under redelivery, in Go.

Task

  • Dedupe by event_id, recorded in the same transaction as the timeline change
  • Guard every change with the activity version: ignore stale edits, never resurrect a delete
  • Commit the offset only after the record is handled
  • Retry transient store errors (3 attempts), then park on the DLQ; poison messages straight to the DLQ
  • Graceful shutdown: finish the in-flight record, take no new work

Acceptance criteria

  • go test -race passes on visible and hidden tests (duplicates, crash between apply and commit, stale and late edits, poison, retries, shutdown, 4 partitions)
  • The live counter equals the number of non-deleted activities after any redelivery
  • No partition stalls behind a bad message
  • ANSWER.md explains why dedupe and mutation share one transaction

backend/x-1 · System design and platform architecture

Scenario. The second-round interview at Lumenfold is a 45-minute system design session: design the workflow automation service that product teams self-serve on Keystone, replacing the CRM's flows. Halfway through, the interviewer adds curveballs (a runaway workflow, a breaking change, an agent caller). You write the whiteboard as you would speak it, then review it like a recording.

Task

  • 45 minutes, timer on: requirements, estimates, API, data model, high-level design, two deep dives
  • At minute 30 read inputs/curveballs.md and answer each in the design
  • Afterwards: self-review in ANSWER.md against the method (what you skipped, where you were vague)

Acceptance criteria

  • Graded by rubric only (grade.sh reports 0/0; the automated row does not apply)
  • Clear split between the engine (Temporal) and the product-facing primitives and API
  • Multi-tenant isolation, quotas and versioning of workflow definitions handled
  • Every curveball answered with a mechanism, not a promise

The migration that took the API down

troubleshootingoptional 2 h

backend/x-2 · PostgreSQL: modeling, indexing, RLS, migrations

Scenario. During the 2026.46 deploy, migration 0057 (a foreign key and an index on activities, 4 seconds in staging) coincided with 11 minutes of 503s from accounts-svc while the database CPU sat at 12%. On call raised the connection pool and restarted pods with no effect, then killed the migration. You get the timeline, pg_stat_activity and pg_locks snapshots, app and job logs, metrics, and the migration.

Task

  • Explain the outage from the lock evidence: who held what, who waited for whom, and why the app stopped
  • Rewrite 0057 as safe migrations that pass kmigrate-lint: lock_timeout, NOT VALID then VALIDATE, CREATE INDEX CONCURRENTLY outside a transaction
  • Prove the end state on PGlite: validated FK, valid index, cross-tenant rows rejected
  • Write ANSWER.md with the root cause, why the pool change did nothing, and the prevention plan

Acceptance criteria

  • make lint clean with the reference linter; make migrate reaches a validated FK and a valid index
  • The FK is added NOT VALID with a lock_timeout and validated in a later migration
  • The index is built CONCURRENTLY in a no-transaction migration
  • ANSWER.md names the lock queue behind the idle-in-transaction session, with evidence
