# ANSWER: backend/w3-c1 Idempotency keys that survive concurrent retries

## Approach

The original code checks for a completed row, runs the handler, then upserts the result. Twenty
parallel retries all see "no row" during the 20 ms directory call, so all twenty run the handler. The
only arbiter of concurrent claims is the database's unique constraint, so the protocol is:
claim (INSERT in_progress under the `(tenant_id, key)` primary key), run, then complete (UPDATE with
status and body) or release (DELETE) on an exception or 5xx. Losers of the claim read the row and
answer 422 (different fingerprint), 409 + Retry-After (in progress) or a replay (completed).

## Fix

`app/idempotency.py`: required key with a length limit (400 problems), fingerprint =
sha256(method, path, canonical JSON with sorted keys), atomic claim with a bounded retry loop that also
replaces rows older than 24 h, release on failure, stored responses replayed with
`Idempotent-Replayed: true` and `application/problem+json` for error bodies. Verified with the visible
tests and a 20-way `asyncio.gather` burst run repeatedly; one account every time.

## Trade-offs / what I would do in production

- Postgres: `INSERT ... ON CONFLICT (tenant_id, key) DO NOTHING RETURNING` for the claim; keep the
  claim in its own short transaction so a long handler does not hold row locks.
- Crash after the handler committed but before the completion write leaves a stuck `in_progress` row.
  Give claims a lease (locked_until) and, better, write the business row and the completion in the
  same transaction (Brandur's "atomic phases") so there is no gap.
- Retention: a nightly delete of rows older than 24 h with an index on created_at; cap stored body size.
- Workflow activities should derive the key from the workflow id and activity id so a retried activity
  reuses it; agents should get keys generated by the tool layer, not by the model.
