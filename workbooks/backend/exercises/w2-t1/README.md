# backend/w2-t1 - The account timeline got slow after release 2026.44

**Type:** troubleshooting | **Estimate:** 1.5-2 hours | **Study plan:** Week 2 (Wed: reading plans, EXPLAIN and pg_stat_statements; Tue: indexes)

## Scenario

It is 15:45 on a Wednesday and you are taking over from Marcus Oyelaran, the SRE on call. Since early
afternoon the account view in Keystone spins for two or three seconds, worst on Lumenfold's biggest
customer, Orbital Freight. The Keystone agent assistant has started timing out when it fetches an
account timeline, and sales ops (Dana Whitfield) is asking every ten minutes. Marcus already scaled
pipeline-svc out and ran `ANALYZE` by hand; neither helped. The team would rather fix forward than roll
back release 2026.44, because it also carries a fix sales ops has waited weeks for.

The database here is real PostgreSQL 18 (PGlite, in process) with the production schema and a
synthetic copy of the data, so you can run the query exactly as pipeline-svc does.

## What you have

| Path | What it is |
|---|---|
| `incident/` | generated by `make setup`: `PAGER.txt`, `oncall-timeline.md`, `p95.txt`, `release-2026.44.diff`, `pg_stat_statements.txt`, `postgres.log`, `explain-2026.43.txt`, `explain-2026.44.txt` |
| `queries/timeline.sql` | the timeline query as shipped in 2026.44 |
| `src/timelineRepo.ts` | the pipeline-svc repository that runs it |
| `scripts/db.js` | opens the database and calls it the way `kdb` (Lumenfold's query wrapper) does |
| `migrations/`, `scripts/seed.sql` | schema and synthetic data |
| `tests/` | visible tests (they pass now: the results are right, only slow) |

## Your task

1. Find the root cause. Prove it with evidence from the bundle and from `make explain`, and rule out the
   other suspects with evidence too.
2. Fix it forward in `queries/timeline.sql` without breaking the reason the 2026.44 change was made.
3. Write `ANSWER.md`: approach, root cause with evidence, fix and verification, and what you would put
   in place so this class of regression does not reach production again.

## Acceptance criteria (what the grader checks)

- The timeline plan seeks the composite index on `account_id` (an Index Cond, not a Filter), with no
  Seq Scan and no Sort, and reads a handful of buffers for the first page.
- Results are row-for-row identical to the pre-incident behavior across pages; tenants stay isolated.
- The query still works when every string parameter is declared as text (how `kdb` 4.0 calls it).
- `ANSWER.md` explains the root cause with quoted evidence; most of the points are for the explanation.

make setup      # toolchain link + incident bundle

make test       # visible tests
# fill in ANSWER.md, then from workbooks/ in Claude Code: /grade backend/w2-t1
