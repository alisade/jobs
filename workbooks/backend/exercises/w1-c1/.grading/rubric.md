# Rubric: backend/w1-c1 Whiteboard write-up: the Keystone platform layer
Pass mark: 70

| # | Criterion | Points | How to judge |
|---|---|---|---|
| 1 | Automated tests | 0 | Does not apply: review-only design exercise (grade.sh reports 0/0) |
| 2 | Requirements and estimates | 15 | Full: functional and non-functional requirements with numbers, explicit non-goals, and arithmetic from volumes.md (activity storage now and in 3 years, about 60 GB now and 150 GB+ with indexes in 3 years; 0.4/s average vs 90/s peak activity writes; read split with the support console at about 1,100 rps; a connection budget) that is then USED to justify a choice. Partial: numbers present but never drive a decision. Zero: no estimates. |
| 3 | Data model | 15 | Full: tenant_id on every tenant table, surrogate keys plus an indexed legacy 18-char CRM id, composite FKs or equivalent so rows cannot reference another tenant, the polymorphic WhoId/WhatId resolved deliberately (typed nullable FKs or a subject table, with the trade-off), custom fields as jsonb with a GIN index and a reason, line items and contact roles modeled, activities designed for the timeline query (keyset index, monthly partitions). Partial: entities listed without keys, tenancy or the polymorphic relation. |
| 4 | Service boundaries | 15 | Full: boundaries by data ownership and capability (for example accounts/contacts, pipeline/opportunities, activities/timeline, automation/workflows, agent gateway), one owner per table, a diagram, and how a service gets data it does not own (API or event-fed read model). Calls out a boundary that is tempting but wrong (for example a shared "CRM database" or a service per table). Partial: boxes by tech layer, or shared tables. Zero: one service with a database everyone reads. |
| 5 | Interfaces | 15 | Full: each capability assigned to API, event, workflow or agent tool with a reason; REST with OpenAPI, versioning, idempotency keys, cursor pagination and RFC 9457 errors; a GraphQL read layer only for reads if at all; an event catalog keyed by aggregate id with a transactional outbox; workflow primitives (assign, approve, escalate, notify, sync); agent tools as task-level operations. Partial: lists endpoints without the sync/async reasoning. |
| 6 | Hidden CRM logic, tenancy and agents | 15 | Full: validation rules become constraints or service checks, flows become workflows, roll-ups become projections, sharing rules become RLS plus explicit cross-tenant roles, triggers each get a named home or are dropped on purpose; tenant model chosen with EU residency handled (separate EU deployment or database for the affected tenant); agents act on behalf of a user via delegated identity so RLS applies, writes are idempotent and risky ones go through a workflow approval, every call is audited. Partial: one or two of these. |
| 7 | Deep dives and migration | 15 | Full: two deep dives on genuinely risky parts with schema, indexes, queries and failure modes (for example the timeline at 400,000 activities per account, the outbox/Kafka path, agent writes); a strangler-fig migration per capability with source of truth per phase, CDC-based sync from the CRM, reconciliation (counts, checksums, sampled diffs) and a rollback per cutover; the finance feed kept working. Partial: big-bang or "dual write" with no reconciliation. |
| 8 | ADRs and clarity | 10 | Full: both ADRs have context, at least two serious options with real trade-offs, a decision and consequences (including the downside accepted); the write-up says what to ask the business; ANSWER.md lists the decisions to defend first. Partial: ADRs that only restate the decision. |
Total: 100
