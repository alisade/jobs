# connect/w2-c3 - Help desk KPI analytics: find what broke first-contact resolution

**Type:** coding | **Estimate:** 2 hours | **Study plan:** Week 2 (Mon: discovery and KPIs; Fri: business analysis and data); Week 7 (Glue/Athena over contact records)

## Scenario

Six weeks into the LFG pilot, the Monday ops review shows the help desk "getting busier": the
steering committee wants to add twelve agents. The service owner suspects a demand problem, not a
staffing one, and asks you for numbers before the CAB meets. You have the contact records (CTRs)
that LFG's Firehose pipeline lands in S3, flattened to Parquet, plus the staffing export and the
change calendar. In production this is Athena over the Glue catalog; locally it is DuckDB, the
same SQL dialect family.

## What you have

| Path | What it is |
|---|---|
| `data/contact_records.parquet` | ~51,000 contacts, 2026-08-24 to 2026-10-04 (generated by `make setup`); timestamps are UTC |
| `data/interval_staffing.csv` | staffed agents per local half hour |
| `data/change_log.csv` | CAB change calendar |
| `queries/q1..q5*.sql` | the analyst's drafts and your answers (one SELECT each, header comments define the output) |
| `findings.json` | your root-cause finding, machine-checked |
| `scripts/run.py` | `make run Q=queries/<file>.sql` prints a result |

Every query runs in a session with `TimeZone = 'UTC'` and three views: `contact_records`,
`interval_staffing`, `change_log`. LFG reports in America/New_York local time: use
`timezone('America/New_York', ts)`. Output columns must be DATE, VARCHAR or numbers (no TIMESTAMPTZ).

## Your task

1. Fix Q1 (weekly volume by driver) and Q2 (weekly AHT per channel) so they match the definitions
   in their headers. Each draft has one realistic mistake.
2. Write Q3: the first-contact-resolution proxy (repeat contact by the same employee about the same
   driver within 7 days) per week and driver.
3. Fix Q4: voice abandon rate by local half-hour interval, weekdays only.
4. Find the root cause of the KPI problem. Write Q5 as your evidence query and fill in
   `findings.json`: `driver`, `change_id`, `change_date` (local), `pre_fcr_rate` (answered contacts
   for that driver in the weeks before the change), `post_fcr_rate` (the first full week after
   it; say in ANSWER.md why not the last week), `excess_contacts_per_week` (mean weekly volume
   after the change minus the mean of the comparable weeks before it).
5. In `ANSWER.md`, write the recommendation for the CAB: what to do instead of (or as well as)
   hiring, with the numbers, and the red herrings you ruled out.

## Acceptance criteria (what the grader checks)

- Q1-Q4 equal the reference results on a freshly generated copy of the dataset (local weeks and
  intervals, abandons excluded from AHT, the repeat definition exactly as written).
- Q5 runs and returns daily rows.
- `findings.json` names the right driver, change and date; rates within 0.012; excess volume in a
  sensible range.
- `ANSWER.md`: evidence quoted from your queries, censoring of the last week explained, the
  recommendation costed against the twelve-agent request, red herrings ruled out.

## How to run

```bash
make setup                                   # shared venv + generate data/
make run Q=queries/q1_weekly_volume_by_driver.sql
make test
# fill in ANSWER.md, then from workbooks/ in Claude Code: /grade connect/w2-c3

```
