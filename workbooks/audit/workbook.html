Agentic audit workbook

Hands-on coding, troubleshooting and design exercises for ControlPilot, the control-testing agent that the internal audit team at Meridian Freight Holdings (fictional) is building. One tab per study week, plus weekly self-exams. Everything grades locally and offline: Gemini is replaced by fake clients and scripted models, Azure by local fakes.

Scores update after /grade; reload the page. Grades come from ../grades/grades.js, written by tools/update_grades.py when you run /grade audit/<id> in Claude Code from the workbooks/ folder. Quiz answers save in this browser (localStorage key wb-audit-v1).

How to work an exercise

  1. tools/doctor.sh audit once: python3 and uv (the venv is built with uv); jq is handy for the incident bundles.
  2. Open the week tab, read the card, then the folder README.
  3. cd audit/exercises/<id> && make setup (the first run builds audit/.venv), solve it, make test, fill in ANSWER.md.
  4. From workbooks/: /grade audit/<id>. Reload this page.
  5. make clean. Retry as often as you like; every attempt is kept.

Do not open .grading/ before you submit. Pass mark 70/100. Troubleshooting is graded mostly on root cause and evidence; design exercises are graded by rubric only (the grader reports 0/0 tests and the automated row does not apply).

How the local stand-ins work

  • Gemini: a fake google.genai client that returns real GenerateContentResponse objects from recorded scripts, and for ADK a scripted BaseLlm subclass driven through the real Runner.
  • Google ADK 2.x runs for real (sessions in memory or in SQLite); MCP servers run for real through the in-memory client.
  • Azure Blob Storage, the GRC system, the change-ticket system and the source-control API are local fakes with the same failure modes (conflicts, pagination caps, timeouts after commit).
  • Troubleshooting bundles (run logs, traces, configs, evidence files) are generated by make setup or shipped in the folder.

Week 1 - Gemini in Python: tool calling and structured outputs

google-genai requests, Pydantic contracts, function calling loops and validation retry, applied to CM-03 evidence. Study guide: Week 1.

Structured CM-03 evidence extraction with Gemini, Pydantic and a validation retry

coding 2-3 h

audit/w1-c1 | Gemini tool calling and structured outputs

Scenario. ControlPilot, MFH internal audit's control-testing agent, asks Gemini to extract the facts for CM-03 (approval before deploy, independent approver, linked change, tests passed) from a change ticket and PR. The prototype's Pydantic model turns missing keys into passing values and a truncated response crashes the run. Make it audit-grade against a fake google-genai client that replays recorded responses.

Task

  • Tighten the ChangeEvidence contract: no defaults, extra keys rejected, aware timestamps, id pattern, citations required
  • Build the google-genai request: temperature 0, JSON with response_schema, two declared tools, automatic function calling off
  • Write a bounded tool loop with an allow-list and a validation retry that feeds the errors back
  • Decide the four attributes in code from the typed facts (instants in UTC, identities through the directory)

Acceptance criteria

  • Contract rejects extra keys, missing keys, naive timestamps and empty citations
  • Disallowed tools never execute; tool errors and validation errors go back to the model
  • Truncated output is retried, SAFETY is not, exhausted retries return needs_review without raising
  • Attribute rules correct across time zones and e-mail aliases; usage summed over every call

Week 4 - Stateful orchestration with human review

Checkpoints, review gates, idempotent side effects and an append-only execution log. Study guide: Week 4.

Durable test run with a human review gate and a hash-chained execution log

coding 2-3 h

audit/w4-c1 | Stateful orchestration and human review

Scenario. ControlPilot tests the Q3 CM-03 sample in one run: evidence, model-backed test, workpaper row in Azure Blob, GRC issue per confirmed exception. Exceptions wait for a human reviewer. The in-memory prototype re-ran every model call after a worker recycle, wrote duplicate workpaper rows and could not show who overrode what. Build the durable version on SQLite checkpoints with local Azure and GRC fakes.

Task

  • Checkpoint every step so a committed step never runs again after a crash and restart
  • Make the workpaper upload and the GRC issue exactly-once (deterministic blob name, Idempotency-Key from run, sample and step)
  • Enforce the review gate in code: reviewer is not the preparer, overrides need a reason and an evidence reference
  • Write a hash-chained JSONL execution log and a verifier that catches edits, deletions and reorders

Acceptance criteria

  • Crash before or after any step, restart: one workpaper per sample, one GRC issue per confirmed exception
  • No committed model or test step executes twice
  • Overrides publish pass with reviewer, reason and evidence; review rules raise ReviewError
  • Log chain contiguous across restarts; verify_log flags tampering

audit/x-2 | Production architecture on Azure and Google

Scenario. Before year end the MFH audit committee, the CISO's architecture review and the external auditor's IT specialist want one document showing how ControlPilot runs in production: Azure hosting, Gemini through Gemini Enterprise Agent Platform via Workload Identity Federation, human sign-off, citations, 7-year immutable retention, a kill switch, and ControlPilot itself under the CM-03 program-change control.

Task

  • Design hosting, durable orchestration and review checkpoints on Azure
  • Design identity (managed identity plus Workload Identity Federation, no keys) and tool scoping
  • Cover data residency, immutable retention, traceability and the execution log
  • Cover evals in CI, change management for prompts and models, threat model and cost

Acceptance criteria

  • Every committee condition maps to a named mechanism
  • Write tools behind approval, no long-lived credentials, idempotent side effects
  • An external auditor can re-perform an item from workpaper and log
  • Cost computed from the stated volumes; rollout with exit criteria
