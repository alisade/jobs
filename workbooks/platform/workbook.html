GCP platform workbook

Hands-on coding, troubleshooting and design exercises for the TechOps platform team at Tessellate Systems (fictional): a GCP org, a four-cluster GKE fleet, Terraform migrations, Crossplane self-service and agents that remove toil without touching prod. One tab per study week, weekly self-exams and two timed mocks. Everything grades locally and offline: no GCP project, no API keys.

Scores update after /grade; reload the page. Grades come from ../grades/grades.js, written by tools/update_grades.py when you run /grade platform/<id> in Claude Code from the workbooks/ folder. Quiz answers and mock results save in this browser (localStorage key wb-platform-v1).

How to work an exercise

  1. tools/doctor.sh platform once: python3, uv and go are all you need.
  2. Open the week tab, read the card, then the folder README.
  3. cd platform/exercises/<id> && make setup (first run builds the shared venv platform/.venv), solve it, make test, fill in ANSWER.md.
  4. From workbooks/: /grade platform/<id>. Reload this page.
  5. make clean. Retry as often as you like; every attempt is kept.

Do not open .grading/ before you submit. Pass mark 70/100. Troubleshooting is graded mostly on root cause and evidence; the design exercise is graded by rubric only (0/0 tests).

How the local stand-ins work

  • Terraform: plan JSON fixtures (terraform show -json shape), HCL parsed with python-hcl2, and a small plan simulator with a mini provider schema (defaults and ForceNew).
  • GCP IAM and Workload Identity Federation: a simulator of the STS exchange and the impersonation binding check, fed with recorded GitHub OIDC claims.
  • GKE: fleet state JSON, and a drain simulator that applies the Eviction API's PDB arithmetic to rendered manifests.
  • Crossplane v2: a render-and-reconcile stand-in for patch-and-transform compositions and provider config lookup; Go exercises use a fake client.
  • Prometheus: a PromQL-subset evaluator over a generated TSDB; ArgoCD: an ApplicationSet and Helm semver resolver.
  • Agents: recorded model responses (Messages API shapes) or deterministic stand-ins; no network, no paid API.

Self-exam

  • Weekly sets (79 questions): week 1: 12, week 2: 12, week 3: 12, week 4: 12, week 5: 12, week 6: 11, AI page: 8.
  • Timed mocks: Staff platform technical screen: 25 questions, 45 minutes; Professional Cloud DevOps Engineer style mock: 25 questions, 50 minutes.

Fleet upgrade planner

coding 2.5-3 h

platform/w2-c1 · GKE and fleet operations

Scenario. Tessellate's four GKE clusters drift onto different versions because upgrades are scheduled by hand in a spreadsheet. Before you automate anything, Dana K. wants a planner that turns fleet state (channels, versions, node pools, maintenance windows and exclusions, quota, PDBs) into an ordered, window-aware upgrade plan with explicit blockers, so the change can be reviewed like a Terraform plan.

Task

  • Build per-cluster steps: control plane one minor at a time, node pools kept inside the version skew, all pools to the target
  • Respect maintenance windows and exclusion scopes (no upgrades, no minor, no minor or node)
  • Order waves dev, stg, prod with canary first, a gap between clusters and a soak between waves
  • Report blockers (channel, PDB with zero disruptions, CPU quota for surge or blue-green, no window) and hold everything after them

Acceptance criteria

  • The fixture plan matches the expected windows and blocks prod-green on quota
  • Exclusion scopes behave like GKE's for minor and patch steps
  • Node pools are never newer than the control plane and never outside the skew
  • A blocked cluster holds every later cluster; CLI exit codes 0 / 1 / 2

On-call page triage assistant with an eval gate

Zero-downtime maintenance strategy for the Tessellate GKE fleet

designoptional 2-3 h

platform/x-1 · GKE fleet operations and zero-downtime maintenance

Scenario. INC-3982 is still open: GKE upgraded prod-blue's node pools in parallel on a Saturday morning with nobody on the bridge, mdm-search went red, a singleton's PDB blocked the drain until GKE gave up, and prod-green repeated it a week later. Stable will offer 1.34 soon and ten more clusters are planned for 2027. Dana asks you, as the staff engineer, for the fleet maintenance strategy and runbook the postmortem never produced.

Task

  • Choose release channels, windows and exclusions per cluster, tied to the staffed calendar and freezes
  • Pick a node pool upgrade strategy per workload class, with settings, quota and cost
  • Define workload readiness requirements (PDBs, probes, singletons, stateful, CronJobs) and how to enforce them
  • Design the fleet rollout order with gates, traffic shifting and rollback
  • Write the runbook for one prod cluster and say how it scales to 14 clusters

Acceptance criteria

  • DESIGN.md covers every template section with GKE-specific settings and numbers from inputs/
  • INC-3982's failure modes are each addressed explicitly
  • Quota and capacity for blue-green are calculated, not assumed
  • ANSWER.md replays INC-3982 under the new design

Chart 3.0 reached every cluster at once

troubleshootingoptional 1.5-2 h

platform/x-2 · Helm and ArgoCD at fleet scale

Scenario. Dana bumped the riq-api canary ApplicationSet to chart 3.0.0 for dev-1 and stg-1 with a 48-hour soak planned. Twenty-five minutes later both prod clusters were CrashLooping on 3.0.0 and Priya was paged for a fast burn on the RIQ SLO. The on-call channel blames the selfHeal change from last week. You get the ApplicationSets, cluster secrets, the chart index, Argo events and app history, and the git log.

Task

  • Reproduce what each cluster resolves with the local ApplicationSet simulator
  • Trace why prod synced 3.0.0 without a stable bump; rule out the red herring
  • Fix the stable ApplicationSet so a new major can only reach prod through a reviewed bump
  • Keep every cluster, including new unlabelled ones, in exactly one wave
  • Root cause with evidence and a safer promotion design in ANSWER.md

Acceptance criteria

  • prod-blue and prod-green stay on 2.x even when newer 2.x and 3.x charts are published
  • Canary clusters stay on a 3.x release; Application names and value files unchanged
  • Every cluster is targeted by exactly one ApplicationSet
  • Root cause names the unbounded targetRevision, with evidence, and explains selfHeal's role
