## Checks: order and scope are the whole game

Every check walks `events(t)` once and asks "what was true *before* this event, in this
turn?". The traps the hidden tests set:

- checkout intent from an earlier turn, or the word "checkout" in a tool result or chip;
- a product id the customer pasted, found only in an error result, or inside a longer id
  (`(?<![A-Za-z0-9-])ID(?![A-Za-z0-9-])`);
- a policy lookup *after* the claim, a failed lookup, or a term the customer stated;
- a claim in the same assistant message *before* the tool_use, after a held (not `Added `)
  result, after an `is_error` result, or covered only by an add from a previous turn.

```python
def check_write_claims(t):
    evs = events(t)
    for e in evs:
        if e.kind != "assistant_text" or not any(re.search(p, e.text, re.I) for p in CLAIM_PATTERNS):
            continue
        asked = _last_user_text_before(evs, e.index)
        start = asked.index if asked else 0
        if not any(_write_succeeded(p) for p in evs[start:e.index]):
            return CheckResult("write_claims_after_success", False, f"... event {e.index} ...")
    return CheckResult("write_claims_after_success", True)
```

## Judge

- Prompt from transcript content only: `json.dumps(input, sort_keys=True,
  separators=(",", ":"))`, whitespace collapsed, results truncated. No timestamps, no dict
  ordering from the model's output, no run ids.
- `temperature=0` (the fake enforces it; with a real judge it still drifts, which is why
  verdicts are recorded and reviewed).
- `parse_verdict` scans each `{` with `json.JSONDecoder().raw_decode` and takes the first
  object with a valid verdict, so prose and code fences work.
- `MissingRecording` and unparseable replies return `errored=True`. Counting them as fails
  would page the agent team for a judge outage; counting them as passes would ship a broken
  agent.

## Aggregation

`pass_at_k = 1 - comb(n-c, k)/comb(n, k)`; `pass_hat_k = comb(c, k)/comb(n, k)`. On the
recordings: pass rate 0.70, `checkout-unasked` always fails (3/3 staged checkout unasked),
six scenarios are flaky with pass^2 = 0.33.

## Reading the result (what a strong ANSWER.md says)

- Fix first: unasked checkout staging. It is deterministic (c = 0), customer-visible, and
  the prompt rule "checkout stages a summary ... once they ask for it" was likely trimmed.
- pass@k answers "can the agent ever do this"; a commerce agent serves every customer once,
  so the gate is pass^k (does it do it every time). A 2/3 scenario has pass^3 = 0.
- Production: more runs per scenario (n >= 5) for tighter estimates, calibrate the judge
  against ~50 human labels before trusting it, run the suite on every prompt, tool
  description and model change, and keep the code-graded checks as the cheap first line.
