# fde/x-2 - PII in decision logs after a "no behavior change" refactor

**Type:** troubleshooting | **Estimate:** 1-1.5 hours | **Study plan:** Week 5 add-on (Thu: exceptions to structured results, Fri: pytest depth); Week 3 (Thu: PII-free decision logs)

## Scenario

Northwind's trust layer (the `agent-trust-commerce` mixin) writes one JSON line per risk
decision to `decisions.log`, which ships to the SIEM. Security signed it off in PR #377:
a `RedactingFilter` masks emails, card numbers and sensitive fields before anything is
written, and `DecisionEvent.customer_email` is `Field(exclude=True)`.

At 06:10 the SIEM paged: tens of thousands of email addresses and card BINs in
`decisions.log`, first seen four minutes after trust-layer 1.14.0 deployed
(`incident/dlp-alert.txt`). 1.14.0 is PR #412, a refactor that only moved code into
modules (`incident/PR-412.diff`). Reviewer B asked about `customer_email`; the author
pointed at `exclude=True` and the redaction filter. Data-handling policy gives you 24 hours
to stop the leak and explain it.

## What you have

| Path | What |
|---|---|
| `trustlog/` | The trust layer's logging as deployed in 1.14.0 |
| `incident/` | The SIEM alert and the PR #412 diff with review comments |
| `run/decisions.log`, `run/dlp-report.txt` | Generated by `make setup`: a replay of yesterday's traffic through 1.14.0 and the DLP scan of it |
| `scripts/dlp_scan.py` | The DLP rules, runnable locally |

## Task

1. `make setup`, read the bundle, and find the root cause. Explain exactly why the redaction
   that worked before PR #412 does not run now, and rule the `exclude=True` theory in or out.
2. Fix it so that redaction cannot be bypassed by any logger under `trust`, today or when
   the next module adds its own logger. `redact.py` was security-reviewed and is correct;
   leave it alone.
3. Verify with `make test` and `make scan` (regenerates the log and re-runs the DLP scan).
4. Write up `ANSWER.md`.

## Acceptance criteria

- No email, PAN-shaped number, or raw `card_bin` reaches the handler's output from
  `trust` or any `trust.*` logger at any depth, including loggers created after
  `configure()` runs.
- Structured fields survive: `decision.decision_id`, `outcome`, `reason_codes`, `amount`
  are intact and `card_bin` is `[redacted]`; message formatting (`%d`, `%.1f`) still works.
- Every record is still written (redaction never drops a line) and trust records stay out
  of the root log.
- `ANSWER.md` names the logging rule at fault with evidence from the bundle and a minimal
  reproduction.
