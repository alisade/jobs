# go/x-1 labelgate: CPU and p99 tripled after a release

**Type:** troubleshooting | **Estimate:** 2 hours | **Week 7 (add-on):** runtime, GC and memory; live debugging

## Scenario

Meridian Telecom's `labelgate` decides which Cortex cluster each metric series is written
to and which labels are added on the way; the remote-write gateway calls it for every
batch. After v2.7.0 rolled out, CPU per pod roughly tripled, p99 went from 9ms to 70ms,
RSS doubled, and the HPA has more than doubled the replica count. The incident channel
wants to rip out the new decision cache. You have real profiles of the running code.

## What you get

- `artifacts/PAGER.txt` (start here), `artifacts/grafana-export.txt`,
  `artifacts/RELEASE-NOTES-2.7.0.md`.
- `artifacts/cpu.pprof`, `artifacts/heap.pprof` - generated by `make setup` from this
  exact code under production-shaped load (`cmd/loadprofile`).
- Source: `router/` (hot path), `server/` (HTTP), `cmd/labelgate`, `config/rules.json`.

## Task

1. Use `go tool pprof` on the profiles to find the regression. Useful views: `-top -cum`,
   `-list 'router.*'`, `-peek`, `-sample_index=alloc_space` vs `inuse_space`, `-http=:8081`.
2. Fix it with the smallest correct change. Keep the public API and routing semantics.
3. Show before/after numbers (`make profile`, `make bench`) and fill in `ANSWER.md` with
   pprof excerpts as evidence. Explain what the heap profile is (and is not) telling you.

## Behaviour that must be preserved

- Rules evaluate in file order, first match wins; `tenant: ""` applies to every tenant.
- Patterns are anchored RE2 (`^(?:pattern)$`); an invalid pattern fails `New`, naming the rule.
- `Decision.Labels` is the input labels plus `add_labels`, never aliases the input or the
  cache; unmatched series get `default_target` and rule `default`.
- `Router` stays safe for concurrent use (`-race` clean).

## Acceptance criteria

- `make test` passes; the loadprofile run after your fix shows a large drop in p99 and
  CPU per request.
- Hidden tests: routing semantics above, plus an allocation budget on the cache-miss path
  measured with `testing.AllocsPerRun` (machine-independent).
- `ANSWER.md` quotes the pprof lines that prove the cause and explains the red herring.

## How to run

```
make setup      # build + capture artifacts/cpu.pprof and heap.pprof
go tool pprof -top -cum artifacts/cpu.pprof
make test
make bench      # BenchmarkRouteCacheMiss with -benchmem
make profile    # after your fix: artifacts/cpu-after.pprof, heap-after.pprof
go tool pprof -top -diff_base artifacts/cpu.pprof artifacts/cpu-after.pprof
```

## What to submit

Your fix in `router/` and a completed `ANSWER.md`, then `/grade go/x-1`.
